#### Team split (illustrative — **not** an ownership declaration)

> ℹ️ The following is **one possible split** illustrating the "each team owns its own pack, zero PR conflicts" property — it is **not** this platform's actual ownership. What actually decides who reviews a PR is [`.github/CODEOWNERS`](https://github.com/vencil/Dynamic-Alerting-Integrations/blob/main/.github/CODEOWNERS). It is deliberately kept out of the inventory table above: every column there is verifiable, and mixing an example in would leave readers unable to tell which parts are fact ([#1277](https://github.com/vencil/Dynamic-Alerting-Integrations/issues/1277)).

- **Databases** (MariaDB / PostgreSQL / Oracle / DB2 / MongoDB / Redis) → DBA team; split per engine to dedicated DBAs once the estate is large enough
- **Search & analytics** (Elasticsearch / ClickHouse) → search / data team
- **Messaging & application runtime** (Kafka / RabbitMQ / JVM / Nginx) → middleware / application-platform team
- **Cluster & platform self-monitoring** (Kubernetes / Exporter Liveness / Operational / Platform) → platform team

Each pack is an independent ConfigMap, so any of these groups can change its own pack without a PR conflict against the others — which is exactly what the Projected Volume architecture buys.

### 3.2 Self-Contained Three-Part Structure

Each Rule Pack contains three separate and reusable parts:

#### Part 1: Normalization Recording Rules
```yaml
groups:
  - name: mariadb-normalization
    rules:
      # Normalization naming: tenant:<component>_<metric>:<function>
      - record: tenant:mysql_threads_connected:max
        expr: max by(tenant) (mysql_global_status_threads_connected)

      - record: tenant:mysql_slow_queries:rate5m
        expr: sum by(tenant) (rate(mysql_global_status_slow_queries[5m]))
```

**Purpose:** Normalize raw metrics from different exporters into unified namespace `tenant:<metric>:<function>`

#### Part 2: Threshold Normalization
```yaml
groups:
  - name: mariadb-threshold-normalization
    rules:
      - record: tenant:alert_threshold:mysql_connections
        expr: max by(tenant) (user_threshold{component="mysql", metric="connections", severity="warning"})

      - record: tenant:alert_threshold:mysql_connections_critical
        expr: max by(tenant) (user_threshold{component="mysql", metric="connections", severity="critical"})
```

**Key:** Use `max by(tenant)` rather than `sum` to prevent HA double-counting (see section 4.3)

The shipped rules also keep the cluster label `da_cluster` in these groupings (`by(tenant, da_cluster)`), so a tenant that runs in several clusters is evaluated per cluster; the threshold layer stays `by(tenant)`. The examples above leave it out for readability; the contract is in [ADR-006](../adr/006-tenant-mapping-topologies.en.md).

#### Part 3: Alert Rules
```yaml
groups:
  - name: mariadb-alerts
    rules:
      - alert: MariaDBHighConnections
        expr: |
          (
            tenant:mysql_threads_connected:max
            > on(tenant) group_left
            tenant:alert_threshold:mysql_connections
          )
          unless on(tenant)
          (user_state_filter{filter="maintenance"} == 1)
        for: 5m
        labels:
          severity: warning
          maintenance: mute   # required: mute | page; generate_rulepack_derived.py writes the two maintenance lines above from it
        annotations:
          summary: "MariaDB connections {{ $value }} exceeds threshold ({{ $labels.tenant }})"
```

#### v2.0.0 Bilingual Annotations (i18n) for Alerts

Starting with v2.0.0, Rule Packs support **bilingual annotations** to enable multi-language notifications:

- **`summary`** (English): Brief alert summary
- **`summary_zh`** (Chinese): Brief alert summary in Chinese (optional)
- **`description`** (English): Detailed explanation
- **`description_zh`** (Chinese): Detailed explanation in Chinese (optional)
- **`platform_summary`** (English): NOC/Platform perspective annotation (used in enforced routing §2.11)
- **`platform_summary_zh`** (Chinese): NOC/Platform perspective annotation in Chinese (optional)

**Alertmanager Fallback Logic:**

Alertmanager templates use Go's `or` function to prefer Chinese annotations when available, with automatic fallback to English:

```go
{{ range .Alerts -}}
{{ with .Labels.da_cluster }}[{{ . }}] {{ end }}{{ .Status | toUpper }}: {{ or .Annotations.summary_zh .Annotations.summary }}
{{ or .Annotations.description_zh .Annotations.description }}
{{ or .Annotations.platform_summary_zh .Annotations.platform_summary }}
{{ end }}
```

The example reads `.Annotations` per alert inside `{{ range .Alerts }}`, not `.CommonAnnotations`: one notification can hold several alerts (several instances, or several clusters of one tenant), `.CommonAnnotations` holds only the annotations that are identical in all of them, and one whose content differs prints as empty. `da_cluster` is the cluster the alert is in (see [ADR-006](../adr/006-tenant-mapping-topologies.en.md)). Each line prints that alert's own `.Status`: with resolve notifications (`send_resolved`), one notification can hold an alert that has resolved next to one that still fires.

This pattern applies to every receiver type that takes a template (email, Slack, Teams, PagerDuty), written in the receiver's `title` / `text` and similar fields; per-type examples are in `k8s/03-monitoring/configmap-alertmanager.yaml`.

**Backward Compatibility:**

- Rule Packs without `*_zh` annotations continue to work — notifications automatically fall back to English
- Existing Prometheus rules need no changes
- In `rule-packs/`, every English annotation (such as `summary`) needs its `*_zh` partner; a missing one is blocked by the `bilingual-annotations-check` pre-commit hook. An alert with no annotations is not checked

For examples, see `rule-packs/` directory.

### 3.3 Advantages

1. **Zero PR conflicts** — each ConfigMap is independent, so teams can push in parallel
2. **Team autonomy** — DBAs own the MariaDB rules without a central platform review
3. **Reusable** — rules port easily to other Prometheus clusters
4. **Independently testable** — each pack can be validated and released on its own

### 3.4 Exporter compatibility: JVM GC time

The JVM pack's `jvm_gc_time_percent` (alerts `JVMHighGCPause` / `JVMHighGCPauseCritical`) is compared with `tenant:jvm_gc_time:percent`: per tenant and per cluster, the share of wall-clock time the **busiest JVM** spends in GC pauses, in percent (5-minute average) — not the sum over the JVMs. Ten JVMs at 7.5% each read 7.5; one JVM at 50% reads 50.

Both naming schemes are read, and a JVM that exposes both is counted once (from Micrometer):

| Exporter | Metric read | Notes |
|---|---|---|
| Micrometer (Spring Boot Actuator) | `jvm_gc_pause_seconds_sum` | One series per `action` / `cause` (plus `gc` from 1.11), summed into one value per JVM first |
| client_java, jmx_exporter | `jvm_gc_collection_seconds_sum` | One series per collector (`gc`); those whose `gc` ends in `Cycles` (`ZGC Cycles`, `ZGC Major Cycles`, `ZGC Minor Cycles`, `Shenandoah Cycles`) are concurrent phases during which the application keeps running, and are left out. `G1 Concurrent GC` is G1's Remark / Cleanup pauses and is counted |

⚠️ **Micrometer version floor**: Micrometer records the concurrent cycles it recognises in `jvm_gc_concurrent_phase_time_seconds`; one it does not recognise is recorded as a pause in full, and the reading is too high. Shenandoah needs 1.7.0 or later, ZGC 1.8.0 or later, generational ZGC (JDK 21 `-XX:+ZGenerational`) 1.12.4 or later, or 1.13.0 or later (1.11.x never got it). This is read from Micrometer's `JvmMemory.isConcurrentPhase` at each version tag, not run.

⚠️ The per-JVM value is summed treating every label other than `action` / `cause` / `gc` as the JVM's identity. An exporter that adds another per-series label to these two metrics splits one JVM into parts and the reading is too low.
