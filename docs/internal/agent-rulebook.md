# Agent Rulebook

受眾是 agent；給人讀的專案規範在 [`dev-rules.md`](dev-rules.md)，兩者刻意分開。每條只有**觸發時刻／約束／機械判準／Traced To**（D-05 另附八軸索引）；為什麼與已知失敗形狀在 [`agent-rulebook-shapes.md`](agent-rulebook-shapes.md)，不確定怎麼套用時才讀。本檔不寫量測數字（owner 2026-09-06 拍板；判準見 [#1620](https://github.com/vencil/Dynamic-Alerting-Integrations/issues/1620)），逐格量測住在 `Traced To` 指向的 issue 與 commit 訊息。正要寫下宣稱時的路由在 `verifying-claims` skill。

## 仲裁：規則互相衝突時

D-01 叫你砍掉守衛，D-04／D-05 叫你補齊守衛，D-06 叫你掃全類別。只有一句：

> **守衛值得留，當且僅當它的靜默失效會讓「它所守的那一類缺陷」無聲通過。**

會 ⇒ D-04／D-05 的射程，補齊。不會 ⇒ 它保護的是它自己，走 D-01 砍掉並把代價寫在原地。判不出來 ⇒ 先跑 D-02（整支還原看有沒有東西轉紅），不靠品味。

## 路由：判準是你站在哪個時點

| 你正在做的事 | 走哪條 |
|---|---|
| 正要寫下一句關於現況的肯定句 | D-09 |
| 正要寫下「沒有 X」 | D-03（D-09 的否定形；驗法不同，要搜能力面） |
| 正要主張「本次改動買到了偵測力」 | D-02 |
| 看到綠燈想知道能不能信 | D-04 |
| 正要設計或修改守衛的述詞 | D-05 |
| 正要判斷既有守衛會不會在真實路徑上跑 | D-04 |
| 拿到 finding 正要動手改 | D-06（先定類別與 N） |
| 要產出那個 N 或任何要寫下的數字 | D-07 |
| 一條線審過好幾輪，每輪審的都是那輪的 diff | D-10 |
| 這一輪的 finding 多半來自上一輪的修法 | D-01，仲裁見上節 |

D-06 與 D-07 是前後段（要數什麼／怎麼數才算數），同時觸發是正常的。

## 全類別掃描的窄豁免

觸發條件是「這個缺陷會不會被照抄或被相信」：會再生（範本、`include`、生成器樣板、fixture 樣板、被文件引用的範例）⇒ 必掃且按再生性排序；會被相信（給使用者看的散文、CLI／告警字串、PR body、CHANGELOG）⇒ 必掃；只影響這一處且沒人會照抄 ⇒ 不必全樹掃，但 commit 訊息要寫「未做類別掃描，理由是 X」，不寫「已修這一類」。⚠️ 本節是一道窄豁免，不是上限——「會被相信」那一格涵蓋散文、CLI／告警字串、PR body、CHANGELOG，絕大多數會寫下來的東西仍落在「必掃」；真正被豁免的只有第三格。

## 規則集怎麼長大

加一條之前問：**有沒有一個具體情境，會讓人不知道該套新規則還是某條既有規則？** 有 ⇒ 併進既有那條。停止條件不是條數也不是大小，先壞掉的是互斥性。退場機制刻意留白：曾寫「兩季無人引用即刪」，實測本檔條目在檔外零引用、`quarterly-audit-sop.md` 沒有一列在看它 ⇒ 那道閘門要嘛不會跑（D-04 的形狀），要嘛第一次稽核就刪光全檔，已撤回。

## D-01 加固會變成主要缺陷來源

**觸發時刻**：多輪修正中，這一輪的 finding 有相當比例出自上一輪的修法。
**約束**：正確動作是**減法**（砍掉加固），不是再寫一層判定。
**機械判準**：本次隨修法一起新增、而把整支修法還原後仍然綠的測試，就不是在測這支修法 ⇒ 砍掉（母體僅限本次新增；例外只有明標的對照組）。判為「保護它自己」的是揭露級不是守衛級，歸宿是 docstring／CHANGELOG 一句「這裡沒有守著」。砍除後對倖存的每一條各跑一格變異（紅＝KILLED、綠＝SURVIVED、不能 parse＝VOID），把代價寫在原地，標明「這是本次撤除的代價」，不要寫成「這裡本來就沒有守衛」。
**Traced To**: #1620 / #1707 / #1702 / #1726 / #1712 / #1632 / #1694

## D-02 宣稱「新增偵測力」要跑 counterfactual，不是 confirmation

**觸發時刻**：正要寫下「這樣一來 X 就會被抓到」「本次買到 Y」。
**約束**：把改動還原，在同一個注入情境下重跑，記錄改動前有多少東西會紅、分別是什麼；差集才是本次的收穫。還原的單位是本次改動的完整 diff。對照組必須落在與目標不同的那一格；每組要有一個「必須成功」的成員；變異後先 parse，不能 parse 判 VOID。
**Traced To**: #1250 / #1284 / #1285 / #1289 / #1294 / #1305 / #1392 / #1428 / #1443 / #1452

## D-03 宣稱「沒有 X」之前要反向搜，而且要搜能力面

**觸發時刻**：寫下任何「沒有 X 涵蓋這件事」的那一刻（含 PR body、CHANGELOG、註解）。
**約束**：症狀面的搜尋不算證據；另做一次能力面的反向搜（「有沒有現成的東西能服務這個需求」），標題與 body 各掃一次、含測試檔，每次帶一個已知必定命中的對照組。找到之後再問「它對我這個維度說得出話嗎」。
**Traced To**: #1203 / #1270 / #1286 / #1347 / #1392 / #1452 / #1549 / #1582 / #1712

## D-04 有 gate ≠ gate 會跑

**觸發時刻**：正要判 CI 綠燈，或宣稱「這個改動有 gate 守著」。
**約束**：**一支斷言「某件事會發生」的守衛，必須讀完所有能讓它不發生的機制。**「檢查 `if:`」是這條的一個實例，不是規則本身；已知的失效層（path filter、hook 未被 workflow 叫到、輸入被截斷、掛在非強制路徑、PR CONFLICTING 時 workflow 不建立、gate 驗的狀態接著被自動步驟摧毀……）逐條在 shapes，每一層都與「gate 正常運作」畫面相同。「零 finding」是歧義訊號不是成功訊號。
**Traced To**: #1223 / #1226 / #1240 / #1270 / #1293 / #1310 / #1327 / #1330 / #1369 / #1402 / #1419 / #1509 / #1648 / #1664 / #1687 / #1689 / #1725 / #1741

## D-05 守衛要可推導，不要列舉語法

**觸發時刻**：寫任何 lint／守衛／分類器／「只准有一份清單」的收攏。
**約束**：不要問「違規會長成什麼樣子」，要問「有沒有一個我能從兩個獨立來源各自推導、然後比對的性質」。測「被接受的集合恰為 S」是性質，測「哪些輸入被拒絕」是列舉。列舉只在集合有一份我以外的權威定義時合法；pin（主張具名對象等於某值）則列舉正是對的。
**八個獨立承重的軸**（每一軸的判別語在 shapes）：a 推導本身會寫錯且更難看見／b 層次選錯述詞再精確都到不了／c 反空轉下限的四種壞法／d 控制項必須呼叫產線那份且與機制同時出生／e 誤紅是第二個維度且是守衛被刪的原因，失敗訊息本身是攻擊面／f 守衛的名字是一句待證的斷言／g 分類那一步要單獨做反例，豁免的可達性要寫成斷言／h 被打穿後問換掉的是問句還是維度。

## D-06 修 finding 要修「類別」，不是被點名的那一處

**觸發時刻**：拿到 review finding 正要改它指的那一行；或正要寫下「已修 `<file>:<line>`」。
**約束**：改寫成「已修這一類，全 repo 共 N 處」；說不出 N 就是還沒掃。類別由「誰消費這個值」定義，判準用後果不用外觀，掃描前先列出承載宣稱的媒介類型（生成物、badge、CLI 字串、docstring、範本、skill 檔、PR body 與留言）。修補本身是這個類別的下一個 instance。

## D-07 掃描與計數：方法、鍵、單位、母體

**觸發時刻**：正要寫下任何數字，或正要宣稱「掃過了／沒有殘留／全部驗過」。
**約束**：計數與掃描一律 parse 結構，不 `grep -c`；任何會被寫下來的數字都算計數。四個獨立軸缺一不可：鍵（自由文字至少三種結構不同的鍵，拿最新那筆打鍵）／比對器粒度（比目標粗放過最像的、比目標窄給假清白）／母體與單位（未截斷未過濾、`wc -c` 是位元組 `wc -m` 是字元、彙總從帳本算）／工具失能（含 CJK 的 pattern 走 Python `re`、先用已知存在的例子測掃描器、判成敗的指令不接管線）。

## D-08 量測與模型衝突時，最危險的解是「修量測」

**觸發時刻**：量測（測試、lint、報告）說「有問題」而心智模型說「沒問題」。
**約束**：修量測前依序成立兩件事：①量測確實有偏差（附證據）②該偏差解釋得了這個特定的不一致。判別語：**我的綠燈，是因為沒有缺陷，還是因為沒有人在看？** 「掃某範圍應為乾淨」的斷言必配 positive control。量測腳本三條硬規則：開跑前斷言樹乾淨、套用變異後回讀驗證且失敗拋錯、還原放 `finally` 並斷言逐位元組相同。
**Traced To**: #1177 / #1407 / #1453 / #1495 / #1508 / #1567 / #1582 / #1598 / #1610 / #1660

## D-09 承重宣稱要先驗證再肯定

**觸發時刻**：正要用肯定句描述「程式碼／設定現在怎麼運作」。
**約束**：先 grep、附 `file:line`，才准用肯定句；設計意見可裸斷言。判別問句：講的是它現在這樣跑，還是該怎麼設計？句子裡有時態就是事實宣稱。「Measured」只能背書量過的那半；遞來的前提也要驗，reframe／reject 是合法第三解。
**Traced To**: #804 / #822 / #825 / #826 / #828 / #942 / #1218 / #1369 / #1386

## D-10 審查的單位決定了它看不見什麼

**觸發時刻**：一條線跑了多輪 review 而每輪審的都是那輪的 diff；或正要宣布「這份東西被審過了」。
**約束**：收尾前補一次以整份檔案為單位的審查；多輪 diff 審查加起來不等於一次整份審查。判準寫下來的當下就是一支 query，立刻對全檔跑一次；關於自己系統的觀察能算就不要寫成散文。
**Traced To**: #1732 / #1795
