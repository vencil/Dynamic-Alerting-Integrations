# Agent Rulebook

**受眾是 agent。** 給人讀的專案規範在 [`dev-rules.md`](dev-rules.md)，兩者刻意分開——維護節奏、語氣、審核標準都不同，而把認識論紀律混進 13 條規範會讓人類讀者找不到規範。

每條的欄位：**觸發時刻**（什麼時候該想起它）／**約束**（一句話）／**為什麼**／**已知失敗形狀**（判準的錨，非窮舉）／**Traced To**（考古，不可變快照）。

⚠️ **本檔因此不是自足的**：冷讀時拿不到判準背後的實證，要看就得開 `Traced To`。這是刻意的取捨——換到的是「不會有人回來改一堆過期數字」。

⛔ **本檔刻意不寫量測數字。** 數字會腐爛而沒有人維護（owner 2026-09-06 拍板；判準見 [#1620](https://github.com/vencil/Dynamic-Alerting-Integrations/issues/1620)）。逐格量測住在 `Traced To` 指向的 issue 與 commit 訊息裡，那裡是不可變快照。

## ⚖️ 這些規則互相衝突時

D-01 叫你**砍掉**守衛，D-04／D-05 叫你**補齊**守衛，而 D-06 叫你**掃全類別**。同一個情境可能同時符合。仲裁只有一句：

> **守衛值得留，當且僅當它的靜默失效會讓「原始缺陷」回來。**

會 ⇒ 這是 D-04／D-05 的射程，補齊它。不會 ⇒ 它保護的是它自己，走 D-01 砍掉，並把代價寫在原地。
判不出來時，先跑 D-02（把它整支還原，看有沒有東西轉紅），不要靠品味。

## 🧭 哪一條適用（規則不互斥，這是路由不是分類）

冷讀實測指出四組會讓人猶豫的重疊。**它們重疊是因為同一個缺陷在不同時點被不同的問句抓到**，所以判準是**你現在站在哪個時點**，不是缺陷屬於哪一類：

| 你正在做的事 | 走哪條 |
|---|---|
| 我**正要寫下**一句關於現況的肯定句 | **D-09**（承重宣稱先驗證） |
| 我正要寫下的是「**沒有** X」 | **D-03**（反向搜；它是 D-09 的否定形，因為否定宣稱驗法不同——要搜能力面而不是讀碼） |
| 我**正要主張**「本次改動買到了偵測力」 | **D-02**（跑 counterfactual） |
| 我看到綠燈，**還沒主張任何事**，只是想知道能不能信 | **D-08**（綠燈是沒缺陷還是沒人看） |
| 我正要**設計／修改**一道守衛的述詞 | **D-05** |
| 我正要**判斷**一道既有守衛會不會在真實路徑上跑 | **D-04** |
| 我拿到一個 **finding**，正要動手改 | **D-06**（先定出類別與 N） |
| 我需要**產出那個 N**，或任何要寫下來的數字 | **D-07**（方法／鍵／單位／母體） |
| 我發現這一輪的 finding 多半來自上一輪的修法 | **D-01**（減法），仲裁見上一節 |

⚠️ **D-06 與 D-07 本來就是前後段**：D-06 決定「要數什麼」，D-07 決定「怎麼數才算數」。同時觸發是正常的，不是重複。

## 💰 成本上限（否則 D-06＋D-07 是無上限的）

冷讀正確指出：照字面把 D-06（全 repo N 處）與 D-07（至少三種鍵、逐條 triage）加起來，**每一個 finding 都要付一次全樹三鍵掃描**，而檔內沒有寫什麼時候可以停。補上：

**全類別掃描的觸發條件是「這個缺陷會不會被照抄或被相信」**，不是「它是不是一類」：
- **會再生**（範本檔、`include`、生成器樣板、fixture 樣板、被文件引用的範例）⇒ **必掃**，且掃描結果按「這一處會不會再生出更多處」排序。
- **會被相信**（寫給使用者看的散文、CLI／告警印出的字串、PR body、CHANGELOG）⇒ **必掃**。
- **只影響這一處、且沒有人會照抄它**（一次性腳本的內部變數、拋棄式 fixture）⇒ **不必全樹掃**，但仍要在 commit 訊息寫明「未做類別掃描，理由是 X」——⛔ **不要寫成「已修這一類」**。

⭐ **判別語**：**我修完之後，會不會有人因為看到這一處被修過，而合理假設整類都被處理過了？** 會 ⇒ 必掃。這正是 D-06 那條「你一旦修了其中一處，讀者就會合理假設這一類已經被處理過」的可操作版。

## 📈 這份規則集要怎麼長大（以及什麼時候該停）

⛔ **停止條件不是條數，也不是檔案大小。** 實測：從五條長到九條，冷讀對頂層規則的抽取率**沒有退化**（5/5 → 9/9），⛔ 標記全數可轉成可執行祈使句。**體積不是那個會先壞掉的東西。**

**先壞掉的是互斥性。** 加一條規則之前，跑這個問句：

> **有沒有一個具體情境，會讓人不知道該套新規則還是某條既有規則？**

有 ⇒ 這一條**不是新的一類**，是既有某條的一個面向 ⇒ **併進去**（D-07 就是這樣由兩張來源卡合併的），或在上面的路由表補一列說明「站在哪個時點走哪條」。

⭐ **退場**：一條規則若在**兩個季度的稽核**中都沒有被任何 PR／commit／review 引用過，就是 dead weight，稽核時強制處置（刪除或併入）。形狀沿用 [`quarterly-audit-sop.md`](quarterly-audit-sop.md) 對 `vibe-*` skill 的問責機制——那裡的判準是「連續 2 季 0 觸發＝強制刪除」。

## D-01 加固會變成主要缺陷來源

**觸發時刻**：多輪修正中，這一輪的 finding 有相當比例出自上一輪的修法。
**約束**：此時的正確動作是**減法**（砍掉加固），不是再寫一層判定。

**為什麼**：加固回應的是「上一輪 reviewer 的問句」而不是缺陷——問句只是缺陷的代理，回應代理會疊層，每一層都是新的受審面。而且交付物有外部成功條件（「假紅消失」可判定），機具沒有（「機具夠不夠好」只能由下一輪 review 定義）⇒ **依建構就不會收斂**。

**機械判準**：把整支修法還原後仍然綠的測試，就不是在測這支修法 ⇒ 砍掉。例外只有明標的對照組（合法呼叫必須續綠）。
**第二判準**：這條加固靜默失效，會不會讓**原始**缺陷回來？不會 ⇒ 它保護的是它自己，那是**揭露級**不是**守衛級**——揭露級的正確歸宿是 docstring／CHANGELOG 裡一句「這裡沒有守著」，不是一支測試。
**證明義務**：砍除後對倖存的每一條各跑**一格變異**（＝把被守護的那段碼做一處最小改壞，看該條是否轉紅：紅＝KILLED、綠＝SURVIVED；變異後先 parse，不能 parse 判 VOID 不計）——否則「刪除」與「刪掉偵測力」不可區分。並把代價寫在原地，標明「這是本次撤除的代價」，不要寫成「這裡本來就沒有守衛」。

**已知失敗形狀**
- 「揭露測試」（記錄這道守衛在哪幾種情況下是錯的）＝該砍的訊號本身，不是該記錄。
- 釘的是性質的**呈現**（訊息措辭）而非性質（exit code）⇒ 每加一句話就是加一個沒有機械 SSOT 的可否證命題。
- 鷹架長得比被保護物大 ⇒ 多數 finding 當然關於鷹架；審查沒失控，是你蓋錯了東西。
- 「我沒有重寫判定式」不足以讓守衛安全——還要問它讀的是判定式的**哪個子集**。
- 加一格前先問：守住新的一類，還是同一類樣本數 +1？後者不加。
- ⛔ **後來更好的修法會讓先前加固所防的情境變成不可達，而沒有人回頭重推導。** 每次補完新守衛後問：「我先前加的哪幾道，它們防的情境現在還到得了嗎？」

**反面**：修掉一個假紅，可能等於拿掉唯一的偵測點。拿掉前問「這件事之後還有誰會看見？」沒有人 ⇒ 同一支 PR 補位。

**散文同理**：(a) 全樹唯一的量測 → 搬進 commit 訊息 (b) 拿掉會讓人重蹈的警告 → 留 (c) 過程敘事 → 刪。

## D-02 宣稱「新增偵測力」要跑 counterfactual，不是 confirmation

**觸發時刻**：正要寫下「這樣一來 X 就會被抓到」「本次買到 Y」。
**約束**：**把改動還原，在同一個注入情境下重跑**，記錄改動前有多少東西會紅、分別是什麼。差集才是本次的收穫。

**為什麼**：「注入 → 轉紅」證明的是**現在會紅**，不是**以前不會紅**。測試框架天然只鼓勵 confirmation；而票／issue 的敘述會先幫你把結論寫好，照抄比查證省事。

**還原的單位是整份檔案**（`git show <base>:<file>`），不是自己挑的行——mutation 證明「測試對這段碼敏感」，counterfactual 要證「測試對**這次改動**敏感」，兩者只在「該段碼＝本次改動」時才等價。

**已知失敗形狀**（都是「對照跑了，但儀器在那個情境下沒有鑑別力」）
- **對照組與目標同值 ⇒ 等於沒有對照**。對照組必須落在與目標**不同**的那一格。任何回傳單一值的量測，都要先證明它回得出別的值。
- **只有 must-fail 的測試組，與「受測物根本沒被呼叫」是同一個畫面**。每一組都要有一個「必須成功」的成員。
- **變異的斷言單位是「紅的原因」，不是「有沒有紅」**。任何讓 harness 爆掉的方式都會給你一個綠字的 RED（語法錯 ⇒ 收集失敗 ⇒ 失敗清單為空 ⇒「必須維持綠」那格偽裝成通過）。前置檢查：變異後先 parse，失敗判 VOID；結果必須含 summary 行。
- **變異在今天是 no-op**（兩個母體今天相同）⇒ 存活由建構保證。先印差集，非空才跑。
- **變異的名字就是一句待證的斷言**。標錯名字＝製造一個看起來有證據的假話。一次只動一個述詞的一個 clause。
- **counterfactual 的對照組不只是「舊版的守衛」，還包括「執行期會不會自己喊」**。宣稱「否則無人偵測」之前，grep 該失效路徑上的 metric／ERROR log／既有告警規則。
- **只量收益不量代價**：「新增偵測 N 條、零轉紅」只量了一半，另一半是「這 N 條的來源，有多少是結構上不該被偵測的」——而「零轉紅」還會**掩蓋**它。
- ⛔ **負向對照回了正值，而我把它從敘述裡換掉了**。寫下「N 種都轉紅」之前，核對我跑的那 N 種是不是我**原本要跑**的那 N 種。差集就是被書寫擠掉的那一格。

## D-03 宣稱「沒有 X」之前要反向搜，而且要搜**能力**面

**觸發時刻**：**寫下任何「沒有 X 涵蓋這件事」的那一刻**——不限開票前，也包含 PR body、CHANGELOG、程式碼註解。
**約束**：症狀面的搜尋**不算證據**。必須另做一次能力面的反向搜尋：不是問「有沒有人記載這個洞」，而是問「**有沒有現成的東西能服務這個需求**」。

**為什麼**：兩者的關鍵字幾乎不重疊。症狀查詢只找得到抱怨與註記；一個已經實作好但沒被連結到你的問題上的機制，在症狀查詢裡是**隱形的**。而「缺口」與「有機制但不可發現」的修法差一個數量級——前者要蓋新東西，後者只要補指路。

**判別語**：這段散文裡有沒有哪一句的真假取決於「**我沒找到**」？有就去搜。「我沒找到」和「不存在」是兩件事，而散文不會替你標出是哪一種。⚠️ 假話通常住在**加強詞**裡（`either`／「任何」把 scope 從「這裡沒涵蓋」偷偷擴大成「全世界沒涵蓋」）。

**做法**
1. 標題掃只覆蓋「別人用跟我一樣的詞命名它」的那些——**還要再掃一次 body**。真正描述症狀的句子通常在 body 裡。
2. 兩次都要帶**必響對照組**——一個你**已知必定命中**的輸入，用來證明這組鍵／這支探針真的抓得到東西。沒有它，「零命中」與「我的查詢寫壞了」是同一個畫面。
3. 搜尋面要含**測試檔**——一份清單的權威副本常常住在釘住它的那條測試裡。
4. 時機是「開始做之前」，不是「做完之後補證明」；後者會退化成替既成事實找理由。

**找到之後還有下半場**
- **「既有工具會報這個拼法」≠「既有工具看得見這個 bug」**。結論是三選一：不存在／存在且覆蓋（→ 補指路）／**存在但只覆蓋拼法不覆蓋語意**（→ 守衛仍要做，理由寫成實測而非推論）。
- 「找到了」之後永遠要再問一句「**它對我這個維度說得出話嗎**」。

**最容易漏的三種觸發**：我是**提案者**時（注意力全在「怎麼做」）／從**環境前提**推論（感覺像在做嚴謹的前提檢查）／**加完守衛之後**才想到要反查。

## D-04 有 gate ≠ gate 會跑

**觸發時刻**：正要判 CI 綠燈，或宣稱「這個改動有 gate 守著」。
**約束**：**一支斷言「某件事會發生」的守衛，必須讀完所有能讓它不發生的機制。**「檢查 `if:`」是這條的一個實例，不是規則本身。

**為什麼**：規則出現在 context 裡不會自動套用。要在「**寫完斷言**」這個時點主動叫用它——本規則被 recall 過之後仍在同一個 session 內復發多次。

**已知的失效層**（每一層都與「gate 正常運作」畫面相同）
- **輸入來源不在 CI 的 path filter 內**——注意是「gate 讀什麼」不是「gate 住在哪」。新增測試時尤其：**會漏的是它讀的別人家的樹**。
- **hook 沒有被任何 workflow 具名叫到**（`git grep <hook-id> -- .github`）。
- **gate 與它的測試跑在不同 job**，而那個 job 的 checkout／工具鏈不足。
- **樣本會過期**（手寫探針集）／**樣本從一開始就不是真的**（fixture 的形狀是 production 從不產生的）。
- **編輯器用萬用字元、CI 用具名清單** ⇒ 有人看得到紅字，但沒有東西會擋。
- **輸入集合被截斷**（API 分頁、`| head`、`-maxdepth`）⇒ 每個分支都 fail-closed，整體仍 fail-open。**fail-closed 是對「查不到」的處置，不是對「查得不完整」的處置。**
- **掛在一條沒有被強制的路徑上**——先找出那個必然會發生的事件，再問「它會不會在不經過我的 gate 的情況下發生」。
- **讀取工具把輸入靜默丟掉**（編碼／locale）⇒ 抽取回空集合，配上「空 ⇒ 都修好了」的下游語意就是一台自動誤報機。
- **我在被守護的程式碼裡加的「保險」讓 gate 結構上不可能紅**。判別語：**我的守衛從哪個位置取樣？我剛加的碼在那個位置的上游還是下游？**
- **`&&` 左側命令的失敗被 errexit 豁免** ⇒ 步驟照樣 exit 0。
- **PR 處於 `CONFLICTING` 時，`pull_request` 的 workflow 一支都不會被建立**——而「沒有 pending」在 check 還沒被建立時就成立。等 CI 要等三件事：具名 workflow 存在＋全 completed＋總數 ≥ 基線（基線 PR 要**與你的 diff 觸及同一組 path filter**）。
- **hook 有跑、印 Passed，但它收不到輸入**（stdin 被中介吃掉／staging area 是空的）⇒ **凡從 stdin／env／argv 取得「要檢查什麼」的 hook，必須有「餵對輸入會紅」的對照組**。
- **沒有任何東西會「安裝」它**——把安裝指令逐字跑一次，檢查它裝出來的東西裡有沒有這道 gate。
- **gate 正確擋下了，但它印的補救指令是空包彈且回 rc=0**（與「修好了」畫面相同）⇒ 把每一條會被印出來的補救，在它會被印出來的那個狀態下逐字跑一次再重試觸發動作。
- ⛔ **gate 驗的是一個「接著會被自動步驟摧毀」的狀態**。判別語：**這道 gate 檢查的那串位元組，和最後落地的那串，是同一份嗎？** 中間只要有任何自動改寫（squash／rebase／bot 補簽／格式化 hook），答案就是「不是」。

**姊妹形狀**：gate 跑了，但它「什麼都沒檢查」也回綠。**「零 finding」不是成功訊號，是歧義訊號**——要能分辨，得看別的量。

⚠️ 一道閘門的**檔頭註解**與**實作**對 fail-open／fail-closed 的說法要**分別讀**：最陰險的誤導來源是守衛自己的文件，而讀者通常只讀那段。

## D-05 守衛要可推導，不要列舉語法

⚠️ **本條是一族，不是一條。** 它的來源在本 repo 是最大的一張，而它之所以大，不是因為囉嗦——是因為底下每個軸都獨立承重。**不要只讀本節的第一句就以為套用了它。**

**觸發時刻**：寫任何 lint／守衛／分類器／「只准有一份清單」的收攏。
**核心約束**：不要問「違規會長成什麼樣子」，要問「**有沒有一個我能從兩個獨立來源各自推導、然後比對的性質**」。列舉式守衛的洞是無限的，可推導式守衛的洞是有限的。

**最短判準**：我釘的是「壞的那些」還是「好的全部」？測「哪些輸入被拒絕」是列舉；測「被接受的集合**恰為** S」才是性質。只有後者對「新增一個好東西」也會說話。

**什麼時候列舉是合法的**：判準不是「可不可以列舉」，是「**這個集合有沒有一份我以外的權威定義**」。有（POSIX 運算子、YAML 鍵、GitHub context 的固定值）⇒ 合法；沒有（「讀環境的方法」「浮動 tag 的字」「壞拼法」）⇒ 一定會有第六個成員。

**pin vs classifier**：我這條斷言，是在對**開放輸入空間**下判斷（⇒ 不可列舉），還是在主張**我這個 repo 的這幾個具名對象等於某個值**（⇒ 列舉正是對的，且任何改動強迫一次 review）？

### D-05a 推導本身會寫錯，而且更難看見
**列舉錯了看得出來（少一個成員），推導錯了看不出來（它讀起來是規則）。** 另外：**範圍可推導 ≠ 規則可推導**，這兩個維度要分開自問。而「我沿用了 X 的判定、沒有重寫第二份」要**逐軸驗**——把判定拆成它實際包含的每一個軸，逐軸問「這一軸我沿用了嗎」。
⛔ **跨語言 oracle**：你的 parser 與它的 parser 對同一段位元組可能給出**不同的型別**，而兩邊都不報錯。問「我讀這個值用誰的 schema？oracle 用誰的？」

### D-05b 層次選錯，述詞再精確都到不了
兩難本身常常是**層次選錯的症狀**：「我是不是在錯的層做這件事？往上一層（未經解析／未經正規化的原始輸入）是不是就沒有這個兩難？」
- 要加「例外／豁免」前先問：**我判斷這個例外所依據的資訊，在我看到它的時候還在嗎？** 被更早的解碼抹平了 ⇒ 例外是依建構存在的洞。
- 我要區分的那兩件事，在我下判斷的那一層還分得開嗎？分不開就往上游移。
- 把「這個東西怎麼被停用」窮舉成一張表、每列標明**住在哪個載體**，再檢查我的述詞讀的是哪一個載體。讀不到的那些列，再怎麼調述詞都不會出現。
- **凡是「先正規化再判斷」的守衛，正規化那一步本身就是攻擊面。**
- 封閉性宣稱要**指名層次**：「對 X 封閉」若不寫出 X，下一個人會讀成「對全部封閉」。

### D-05c 反空轉下限的四種壞法

（**反空轉下限**＝一條「掃描到的東西不得少於 N」的斷言，用來擋「守衛跑了但語料是空的」這種假綠。）
- 不可取自它要保護的東西（兩邊一起縮）。
- 不可架在**不會動的數**上——把下限指標放進「守衛失效」的情境跑一次，它會動嗎？
- 不可架在**今天恰好如此的巧合**上（那樣它最便宜的轉綠方式就是刪掉它）。
- 不可是判定式的**平行重寫**（判定式歸零時它不動＝保護的是自己）。
⛔ **要刪一個下限之前，先問「它現在實際上守著哪一個軸」**——一個下限可以同時對 A 軸無效、對 B 軸有效。
⭐ **集合相等比數量下限強，但它不含 anti-vacuity**（兩邊同時歸零時 `0 == 0` 完美成立）⇒ 必須指名「誰在守空集」。
⭐ 真正獨立於被保護對象的是**合成案例**，不是下限：這條斷言的輸入，會不會經過我要保護的那條路徑？不會 ⇒ 它才是獨立的證人。

### D-05d 控制項
- **控制項必須呼叫產線那份**，不是重寫一份等價的。把判定抽成純函式，讓產線與控制項呼叫同一個名字。
- **控制項守的是函式，洞可能在呼叫點。**
- **新機制的控制項要跟它在同一次編輯裡出生**——`grep` 你剛加的識別字，看它在「負向控制」區出現幾次。**零次＝那個機制從出生就沒人看守。**
- 反例要**成對**：只釘「繞過會被抓」不夠，收緊分類器可以靠**全部拒絕**通過那一半。
- 用**任意**輸入（一個不存在的成員）才能區分 accept-set 與 denylist；用真實輸入永遠區分不了。
- ⛔ **控制項的鑑別力可能來自直譯器／平台而不是被測的碼**。我這條斷言讀的字串，是我寫的，還是別人（stdlib／框架）格式化出來的？

### D-05e 誤紅是第二個維度，而且它才是守衛被刪掉的原因
- **每寫完一條守衛，除了問「能不能繞過」，必問「最便宜的轉綠是什麼，它會不會打開洞」。**
- **誤紅面必須在選述詞之前量**，否則會選錯軸。
- 修誤紅時問：**我的修法是縮小誤判，還是縮小涵蓋？** 兩者的畫面都是「紅的變綠了」。
- ⛔ **失敗訊息本身是攻擊面**。訊息若指名了「比較便宜但比較壞」的修法，守衛會被照著它做的人拆掉。並且問：**照著這則訊息做，走得到綠嗎？** 走不到 ⇒ 它不是指引，是把人推向下一個縫的路標。
- 守衛檢查不到的修法配方＝**一個附了說明書的洞**。
- **誤報有時是在指出被檢查方寫錯，不是守衛寫錯。**

### D-05f 描述與名字
- **守衛的名字就是一句待證的斷言**——念一次，body 證得出那句話嗎？（註解騙的是下一個讀者，**名字騙的是寫測試的我自己**。）
- 守衛的訊息／註解在描述它自己時，念出來的應該是**那個判定式**，不是滿足判定式的幾個例子。**過期的描述比沒有描述更糟。**
- ⛔ **註解擋不住任何機器。**
- **既有測試會替缺陷作證**——凡是 reviewer 反覆看過卻沒發現的缺陷，先問「有沒有一條測試正在替它作證」。⭐ **反過來也成立**：收到「這裡少一條檢查」的 finding 時，先 grep 有沒有測試在斷言相反的事。

### D-05g 分類與豁免
- **列舉式守衛最惡劣的失敗不是「判錯」，而是「不把它當受檢對象」**——分類器的漏接會偽裝成通過。任何「先分類、再檢查」的守衛，要對**分類那一步**單獨做反例測試。
- **自己為方便加的旋鈕就是自己守衛的後門。**
- **分類是被「宣告」的還是被「建構方式決定」的？** 可宣告 ⇒ 可宣告錯 ⇒ 遲早有人宣告錯。
- **豁免的可達性論證本身要被寫成斷言**；散文沒有東西讀它。
- 要守的是「意圖」而證據只有「當下狀態」時，任何判別式都不可能成立 ⇒ **引用一個權威不在自己身上的既有契約**（讀它宣告的集合，不要重跑它、也不要抄一份）。
- **一個反例只有在「它是該範圍內唯一的攔截者」時才作得了證**——多重過濾串聯時，逐個問「拿掉它，這個 fixture 會走到哪裡」。**被遮住的不是性質，是我挑的那個投影。**

### D-05h 收斂與停止
- **「我覺得收斂了」不是停止條件**；停止條件是某一輪**真的**零可繞過缺陷。
- 每次被打穿之後問：**我換掉的是問句還是維度？** 換維度只是把同一個列舉搬個家。
- 兩個候選述詞都只是近似時，先問「它們今天的產出差幾條」——差 0 就別再比偵測力，改比「**它們各自錯的時候會讓人做什麼**」。
- **「跑得起來」與「會失敗」是兩個軸**，只修前者比不修更糟（從「永遠紅、沒人看見」變成「永遠綠、而且有人看」）。
- ⭐ **可推導的守衛通常比列舉貴，寫完看一眼耗時。**

## D-06 修 finding 要修「類別」，不是被點名的那一處

**觸發時刻**：拿到 review finding，正要動手改它指的那一行；或正要寫下「已修 `<file>:<line>`」。
**約束**：把那句話改寫成「**已修這一類，全 repo 共 N 處**」。**說不出 N 就是還沒掃。**

**為什麼**：finding 是以「一個座標」的形式送到的，注意力就停在那個座標上。而缺陷的真實範圍是一個**類別**——同檔的其他函式、姊妹工具、同一份設定的其他區塊、以及**描述舊行為的所有散文**。

⭐ **新一層**：不要只是「沒停在被點名的那一行」——**也不要停在被點名的那個函式**。推導出「為什麼這裡是錯的」之後，**那個「為什麼」就是新的掃描鍵**，拿它掃全部入口。改完問一句：**這支 PR 對 A 做的每一件事，B 都做了嗎？** 兩個平行入口是現成的對照組，不用等 reviewer 給。

**掃描前先想清楚三件事**
1. **類別由「誰消費這個值」定義，不是由「這個值長什麼樣」定義。** 自我檢查句：**我的掃描鍵，是不是就是我已經看到的那個 bug 的形狀？** 是 ⇒ 這個掃描只找得到同形狀的雙胞胎，找不到同**語意**的表親。
2. **界定類別的判準用「後果」不是「外觀」**——「照抄會不會出錯」，不是「長得像不像」。先用真實 `--help` / 真實 loader 當 oracle 建立判準，再拿判準去掃。
3. **先列出承載這個宣稱的媒介類型**，比想詞形有效且穩定：生成器產物／README badge／CLI 與告警**印給人看的字串**／dashboard `description`／測試 docstring／範本與 `include` 檔／skill 檔／**PR body 與 GitHub 留言**。

**已知失敗形狀**
- ⛔ **finding 說「你這份清單漏了一個」時，補成員是最自然也最糟的修法**——斷言的**形式**原封不動，而清單變長變具體，**讀起來像嚴謹度在上升**。先問：這句話的形式是不是要求我窮舉一個**會長大**的集合？是 ⇒ 換形式（明示非窮舉＋安全預設），或**移除那個描述維度**。⭐ **看到一份很具體的清單時要更警覺，不是更放心。**
- **多條 finding 同源時，移除上游，不要逐條修**——逐條修會讓下一輪再長出一條。
- 「這個缺陷不是我造成的」**不構成不修的理由**：你一旦修了其中一處，讀者就會合理假設這一類已經被處理過。
- **掃描結果要按「這一處會不會再生出更多處」排序**——範本檔、`include` 檔、fixture 樣板加權最重。
- **無人讀取但仍在斷言舊契約的產物**（孤兒 golden／fixture）要掃到；判別法是對每個命中問「誰讀它？」，答案是「沒有」時**刪掉，不要更新**。
- **改行為時，掃描鍵是那個行為的形容詞，不是函式名**（`silent`／`靜默`／`no error`／`swallow`）。⚠️ **半真的敘述最難掃**：改完後可能只有半句不成立——要逐句拆成獨立命題各自判真假。
- ⛔ **修補本身就是這個類別的下一個 instance。** 修完一批 finding 後，把那批 finding 的規則**逐條套回自己的修補**，並問「**我剛動過的那一半，還是我以為的樣子嗎？**」
- ⛔ **要把一個修法寫成「類別敘述」時，先把那段敘述當成 query 對自己的模組跑一次**——它對這個檔裡還有誰成立？
- ⛔ **當你把「我修好了這一類」寫進 CHANGELOG／commit／docstring 的那一刻，那句話本身就是待驗宣稱**：先跑一次全 repo 掃描，把 N 填進去，再寫下那句話。⭐ **嚴重度不是優先序**——最低等級的 nitpick 可能指向核心斷言的靜默失效路徑。
- **「過度宣稱」是獨立的一類**：寫下「內建／自動／可證明／保證／純／免疫／不受影響」之前，問**「這句話對應到哪一行程式碼？指得出來嗎？」** 指不出來就是散文在替機器背書。⚠️ 但不是所有絕對語氣都是過度宣稱——掃描時要保留判準。
- **已發布的假話要發更正留言，不是靜靜改掉 body。**

## D-07 掃描與計數：方法、鍵、單位、母體

⚠️ **本條由兩張來源卡合併**（「計數走 parse 不走 grep」與「比對法比目標粗糙會藏住漂移」）。合併的理由就是 D-01 的判準：它們是同一類的不同入口，分兩條只是把同一類的樣本數 +1。**因此要做的不同事**：不要只讀 D-07a 就以為套用了它——四個子節（鍵／粒度／母體與單位／工具失能）對應四種**獨立**的失敗，任何一個沒過，這個數字就不成立。

**觸發時刻**：正要寫下任何數字，或正要宣稱「掃過了／沒有殘留／全部驗過」。
**約束**：**計數與掃描一律 parse 結構**（`yaml.safe_load` / AST），不要 `grep -c`。**任何會被寫下來的數字都算計數**——包含「還剩幾處」「大約幾個」「規模是 N」。**估算不是豁免，寫下來就是宣稱。**

### D-07a 鍵
- **鍵不可憑印象挑。** 挑好鍵之後，**拿「我最近加進去的那一筆」去打它**——打不中就是鍵錯了，不是資料錯了。憑印象挑的鍵會系統性漏掉**最新的、格式最不典型的**那幾筆。
- **鍵要挑「語言層真正建立的那個關係」，不是「內容裡剛好出現的字串」。** 後者對重新命名、別名、`from X import Y`、動態組裝一律盲，而且**盲的方式是回報零**。
- ⛔ **一種鍵只看得見一種載體。** 判別語：**我這個 N 是幾種鍵掃出來的？只有一種 ⇒ 它一定漏了那種鍵看不見的載體。** 至少三種在結構上不同的鍵：數字＋英文名詞／數字＋**CJK 量詞**／**不含數字的識別字**（工具名、hook 名）——最後一種才抓得到改寫過措辭的副本。取聯集後**逐條 triage**（寬鍵會帶進假陽性）。
- **互補寫法**要各自一組鍵：`the other N-1`、`N of M`、「除了…以外」、括號／粗體／單位詞變體。

### D-07b 比對器的粒度與寬窄
- **比對器比目標粗糙 ⇒ 系統性放過最像目標的案例**（舊名是新名的前綴時，子字串法一律回報「找到了」）。
- **比對器比目標窄 ⇒ 給假清白**：逐行 grep 對**折行切開的識別字**是盲的，而它回報的是「乾淨」不是「未知」。判別語：**我的比對法，會不會因為目標的排版（折行／大小寫／空白）而失效？**
- ⛔ **我的掃描器與我要找的缺陷，是不是同一個形狀？** 找折行的東西就不能逐行掃；找被截斷的東西就不能用會截斷的管線；找被正規化抹平的東西就不能在正規化之後比對。
- **同一個東西可能有兩種身分寫法，而兩種都是對的。** 盤點前先隨機讀 2–3 個**不同來源**的實例，不要從一個實例推出 pattern。
- **搜尋短工具名之前，先想它會不會是別的字的子字串**（`ruff` ⊂ `trufflehog`）。假陽性比漏抓更陰險——**漏抓讓你少做一件事，假陽性讓你據以做出方向相反的決定。**

### D-07c 母體與單位
- ⛔ **N 必須來自未截斷、未過濾的輸出。** 先 `wc -l` 拿總數再決定要不要 `head`；用「我以為會受影響的東西」寫的過濾器，輸出必然只含我的預期集合＝用假設驗證假設。
- ⛔ **我這條 pipeline 有沒有哪一段在我不知道的情況下把檔案濾掉了？**（`^./.git` 會配到 `.github`。）正解是**根本不要事後過濾**：用 `git grep` 或 `--exclude-dir`。
- ⛔ **票面點名的檔案清單是起點，不是母體。** 說「全 repo N 處」時，我的掃描器的輸入真的是全 repo 嗎？
- **修一個計數缺陷（重複、雜訊、誤配）時，要把修法本身當成新的計數缺陷來驗**——「我這個修正排除了什麼？那些是不是也該算？」
- **單位**：`awk length` / `${#var}` / `wc -c` 是**位元組**，`wc -m` / Python `len(str)` 是**字元**。CJK 語料會把每一次不一致放大三倍，而**單位錯的方向永遠是「少算了最相關的那些」**。
- **彙總數字一律從帳本或原始紀錄程式算一次**——不手數、也不沿用自己上一句話裡的數。算完把**基礎**寫在數字旁邊。
- **宣告面查得到的永遠是子集**（規則的 `labels:` vs expr 帶出來的 label）。要斷言「執行期會怎樣」就得把執行期的產生途徑全部列出來。

### D-07d 工具本身會失能，而失敗長成「零命中」
- ⛔ **含 CJK 的 pattern 一律走 Python `re`**：`grep -E` 的 `.`／`?` 配的是**位元組**，中文一律回報「找不到」——**與「真的沒有」完全同形**。要用 grep 就只用純字面。
- ⛔ **宣告「掃過了／沒有殘留」之前，先用一個已知存在的例子測掃描器本身。** 掃描器壞掉的輸出是 0 個匹配，掃乾淨的輸出也是 0 個匹配。**空集合是最該被複驗的結果。**
- **要判成敗的指令不要接管線**（pipeline 的 rc 是最後一段的）；`grep -c` 零匹配 exit 1。
- **`find()`／`index()`／切片式取樣當「驗證」用時，必須先斷言 `i >= 0`**——`-1` 會悄悄變成「最後一個字元」。
- **有配對／巢狀／跳脫語意的東西，regex 一定會在不成對的輸入上失效**，而不成對正是散文裡最常見的形狀。
- ⛔ **重現不出一個已發布的數字時，列舉多種結構上不同的定義各報一次，證明目標值不在其中**——才分得開「我算錯」與「我們定義不同」。處置是**把定義寫進同一個句子**，不是換一個下次還會對不上的數字。

## D-08 量測與模型衝突時，最危險的解是「修量測」

**觸發時刻**：一個量測（測試、lint、報告）說「有問題」而我的心智模型說「沒問題」。
**約束**：修量測之前必須**依序**成立兩件事，缺一不可——①量測確實有偏差（附證據）②**該偏差解釋得了這個特定的不一致**，而不只是「量測本來就不完美」。

**為什麼**：修量測會**刪掉真問題的證據**，而且刪完之後數字變好看，看起來像成功。

**共同判別語（本條的核心）**
> **我的綠燈，是因為沒有缺陷，還是因為沒有人在看？**

**已知失敗形狀**
- **閘門版**：「告警歸零」與「偵測器被拿掉」畫面完全相同。關「守衛修好了」的票之前，**數偵測器本身**（走 AST 數規則字典），不要讀它的輸出；差額要**逐條交代得出來**。
- **測試版**：`assert run() == []` 會被任何「少掃一點」自動滿足。⇒ 凡是「掃某範圍應為乾淨」的斷言，**必配 positive control**——在拋棄式樹裡種下已知缺陷，斷言每一種 check 都回報；再加一格斷言**掃描面清單的內容**。
- **綠燈有兩種成因，同一次觀察分不出來** ⇒ 要跑**兩種**擾動：「保證改變輸出」的擾動量**可達性**、「你真正關心的那個旗標」的擾動量**鑑別力**。只跑後者會產出一張**方向相反**的覆蓋地圖。
- ⛔ **不要問「今天的回報會不會變」，要問「有幾個原本活著的比對變成不比對了」。** 一個只比較「工具印了什麼」的 oracle，對「工具還在不在看」完全失明。
- **有人在看，但看的是另一條路徑**：一張參數化的「各種壞形狀」表，除了問「型別涵蓋了嗎」，必須再問**每一列是怎麼走到被測的那一段的**——樣本值的**次要性質**（truthy/falsy、長度非零）常常就是那個分岔。
- **「沒有副作用」的斷言，快照範圍必須涵蓋「這個缺陷可能把東西放到的每一個地方」**，而那份清單要從**缺陷敘述**推導，不是從我測試裡剛好 chdir 到的那個目錄推導。
- ⛔ **同一個實驗三次三個值 ⇒ 拿掉數字，不是修正數字。** 判別語：**這個數字換一個人、換一台機器、換一個呼叫順序重跑，會不會一樣？** 不會 ⇒ 它是量測 harness 的性質，不是被測物的。

**量測腳本的三條硬規則**
1. 開跑前**斷言樹是乾淨的**，基準才有資格叫基準。
2. 套用變異之後**立刻回讀驗證**，並讓「套用失敗」**拋錯**而不是回傳 0——「沒量到」與「量了沒事」必須不同形。
3. 還原放 `finally`，收尾**再斷言逐位元組相同**。

⚠️ **當某一列的結果與預期相反時，先問「這一列量的真的是我以為的那個條件嗎」，再去修理論。**
⚠️ **`--fix` 類工具不是唯讀的驗證指令**——它會寫入它找得到的任何檔；跑完一律 `git status` 複查。

## D-09 承重宣稱要先驗證再肯定

**觸發時刻**：正要用**肯定句**描述「程式碼／設定**現在**怎麼運作」。
**約束**：那是 **hard verify-first 區**——先 grep、附 `file:line`，才准用肯定句。**設計意見（該怎麼設計）可以裸斷言。**

**判別問句**：我是在講它**現在這樣跑**（verify-first），還是它**該怎麼設計**（opinion-OK）？
⭐ 附帶一個機械線索：**這句話裡有沒有時態**（發生過／會發生）？有 ⇒ 它是事實宣稱，不是設計意見。

**觸發條件**（避免「驗一切」）：三者皆中才強制先驗——描述當前行為 ＋ 有決策壓在上面 ＋ 錯了代價高。

**已知失敗形狀**
- ⛔ **這個病的形狀不是「查證不足」，是「論述需要更有力時，補強的那一句最不會被查」。** 觸發時機固定：**當你正在寫一句用來說服人的理由時**。
- **「Measured」這個詞會替它後面整段背書，包括你沒量的那半。** 判別語：**我量的那個情境，和我用它支撐的那句話，是同一個情境嗎？** 不是 ⇒ 量到的寫成量到的，推論寫成推論，兩句話分開。
- **遞來的前提也要驗**：task／外審把題目 framed 成「修違規 X」並附 A/B 選項時，先驗 X 是否真的成立再選——**reframe / reject 是合法的第三解**。
- **「不在我 tree」≠「不存在」**：前提指名某 PR 而你 grep 不到時，先查**未合併的 sibling PR**。
- **長開 PR 的 claim 會過期**：finalize 前 `git fetch` 並對**當前 tree** 逐條重驗。最毒的形態是你寫的「已知缺口／另行追蹤」註記，已被 sibling PR 修好。
- **寫進永久註解的「歷史敘事」比寫進回覆的更該驗**。說「過去發生過 X」→ `git log --all -- <path>` 並看那顆 commit **還動了什麼**；說「壞會落在下游 Y」→ 讀 Y **自己的** trigger。⭐ **「結構上可達、尚未燒到」是完全站得住的論證**，不需要編一個事故來加強它。
- **安慰性的補充句最缺乏審查**（「別擔心，還有 Y 會擋」）——它讀起來像在讓話變得更完整。判別語：**我量的是「這支工具的行為」，還是「那條路徑上實際被呼叫的那一行」？**
- ⛔ **不要在驗證指令後面接一句寫死的 `echo` 結論**。判別語：這行 `echo` 的內容，**會因為上一個指令的輸出不同而改變嗎？** 不會 ⇒ 它不是驗證，是自我暗示。讓結論由資料算出來，或乾脆不寫結論。

**配套**：信心標記只貼**承重** claim（`[已驗 file:line]` / `[推測]` / `[未查]`），全標＝噪音；claim 若對映真實 gate，**引那個 gate** 而不是引我的閱讀。
