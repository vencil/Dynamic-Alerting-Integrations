## Overview

This guide covers how to implement fully automated Operator path deployment in GitOps (ArgoCD / Flux) workflows using CRD YAML generated by `operator-generate --gitops` (PrometheusRule, ServiceMonitor) and the Alertmanager config Secret produced by `generate-routes`.

## Generate GitOps-friendly YAML with da-tools

```bash
da-tools operator-generate \
  --rule-packs-dir ./rule-packs \
  --output-dir ./prometheus-operator-crds \
  --gitops

# --gitops effect:
#   - sorted keys (deterministic output)
#   - no timestamps, resourceVersion, status
#   - ArgoCD / Flux won't report false OutOfSync
```

Alert routing is not a CRD: `generate-routes` merges conf.d into your source and the output is wrapped in a Secret (procedure and Alertmanager CR settings: [Operator Alertmanager Integration](operator-alertmanager-integration.en.md)):

```bash
da-tools generate-routes --config-dir ./conf.d --output-alertmanager \
  --base-config ./alertmanager/alertmanager.base.yaml -o alertmanager.yaml
kubectl create secret generic da-alertmanager-config -n monitoring \
  --from-file=alertmanager.yaml --dry-run=client -o yaml \
  | kubeseal --format yaml > secrets/da-alertmanager-config.yaml
rm alertmanager.yaml                  # the plaintext output stays out of Git
```

When conf.d changes, rerun with the same `alertmanager.base.yaml`; never use the produced `alertmanager.yaml` as the next base.

## ArgoCD Integration

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: dynamic-alerting-operator
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/your-org/monitoring-config
    targetRevision: main
    path: prometheus-operator-crds/
  destination:
    server: https://kubernetes.default.svc
    namespace: monitoring
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

### CI Pipeline Example

```yaml
# .github/workflows/update-crds.yml
name: Update Operator CRDs
on:
  push:
    paths: ['conf.d/**', 'rule-packs/**']

jobs:
  generate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - name: Generate CRDs
        run: |
          docker run --rm \
            --user $(id -u):$(id -g) \
            -v ${{ github.workspace }}/conf.d:/conf.d:ro \
            -v ${{ github.workspace }}/rule-packs:/rule-packs:ro \
            -v ${{ github.workspace }}/prometheus-operator-crds:/output \
            ghcr.io/vencil/da-tools:v2.9.0 \
            operator-generate --gitops --rule-packs-dir /rule-packs --output-dir /output
      - name: Render Alertmanager config
        run: |
          docker run --rm \
            --user $(id -u):$(id -g) \
            -v ${{ github.workspace }}/conf.d:/conf.d:ro \
            -v ${{ github.workspace }}/alertmanager:/alertmanager \
            ghcr.io/vencil/da-tools:v2.9.0 \
            generate-routes --config-dir /conf.d --output-alertmanager \
              --base-config /alertmanager/alertmanager.base.yaml -o /alertmanager/alertmanager.yaml
          kubectl create secret generic da-alertmanager-config -n monitoring \
            --from-file=alertmanager/alertmanager.yaml --dry-run=client -o yaml \
            | kubeseal --cert sealed-secrets.pem --format yaml > secrets/da-alertmanager-config.yaml
          rm alertmanager/alertmanager.yaml
      - name: Commit & Push
        run: |
          git add prometheus-operator-crds/ secrets/da-alertmanager-config.yaml
          git diff --cached --quiet || git commit -m "chore: update operator CRDs"
          git push
```

⚠️ The v2.9.0 image has no `generate-routes --output-alertmanager`, and its `operator-generate` `all` still reads conf.d and emits per-tenant AlertmanagerConfigs; the pipeline above needs a da-tools newer than v2.9.0. <!-- image-caveat: v2.9.0 -->

## Secret Management

Receiver sensitive information (Webhook URLs, API Keys, etc.) **must never be committed in plaintext to Git**. Recommended solutions:

### Sealed Secrets

```bash
kubeseal --controller-name=sealed-secrets \
  --controller-namespace=kube-system \
  --format yaml < secret-slack.yaml > sealed-secret-slack.yaml
```

### External Secrets Operator

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: da-db-a
  namespace: monitoring
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: da-db-a
  data:
    - secretKey: webhook-url
      remoteRef:
        key: dynamic-alerting/db-a/slack
        property: webhook-url
```

## Migration Path: ConfigMap → Operator CRD

### Phase 1: Parallel Run (1 week)

Deploy both ConfigMap and CRD simultaneously, compare alert output:

```bash
# Keep old ConfigMap
kubectl get configmap -n monitoring | grep prometheus-rules

# Add PrometheusRule CRD
kubectl apply -f prometheusrule/

# Check for conflicts
kubectl logs -n monitoring prometheus-kube-prometheus-stack-prometheus-0 | grep -i "duplicate"
```

### Phase 2: Switch Alert Routes (1 day)

On the ConfigMap path the source is the ConfigMap's `alertmanager.base.yml`; use it as the base, produce the Secret, then point the Alertmanager CR's `spec.configSecret` at it ([Operator Alertmanager Integration](operator-alertmanager-integration.en.md) Step 4):

```bash
kubectl get configmap alertmanager-config -n monitoring \
  -o jsonpath='{.data.alertmanager\.base\.yml}' > alertmanager/alertmanager.base.yaml
# produce and apply secrets/da-alertmanager-config.yaml as in "Generate GitOps-friendly YAML with da-tools" above
kubectl apply -f secrets/da-alertmanager-config.yaml
curl -s http://localhost:9093/api/v2/status | jq -r '.config.original' | head -40
```

### Phase 3: Clean Up ConfigMap (1 day later)

```bash
# Backup
kubectl get configmap -n monitoring -o yaml > backup-configmaps.yaml

# Delete old ConfigMap
kubectl delete configmap prometheus-rules-mariadb -n monitoring
```

### Rollback

```bash
kubectl apply -f backup-configmaps.yaml
kubectl delete -f prometheusrule/
```
