## Overview

Prometheus Operator 環境下，告警路由與 ConfigMap 路徑由**同一個產生器**渲染：[`da-tools generate-routes`](../cli-reference.md#generate-routes) 把 conf.d 的租戶路由合併進你自己的 Alertmanager 設定，輸出一份完整的 `alertmanager.yaml`；你把它放進一個 Secret，再讓 Alertmanager CR 的 `spec.configSecret` 指向它。Operator 路徑上由 `operator-generate` 產生的只有 PrometheusRule 與 ServiceMonitor（見 [Operator Prometheus 整合](operator-prometheus-integration.md)）。

輸出的 `route.routes` 順序與 ConfigMap 路徑相同：平台 4 條路由（Watchdog 心跳、`component="custom"` 隔離子樹與其下各租戶的子路由、synthetic probe、sentinel）在最前面，接著是你的 base 自己的路由（原順序），最後是租戶路由。base 是來源，不是先前的輸出（輸出第一行是 `# GENERATED by da-tools generate-routes` 標記，帶這一行的 base 會被拒收）。合併規則與結束碼見 [cli-reference §generate-routes](../cli-reference.md#generate-routes)。

**為什麼不用 AlertmanagerConfig CRD**（[#3572](https://github.com/vencil/Dynamic-Alerting-Integrations/issues/3572)）：Prometheus Operator 把 AlertmanagerConfig CR 的路由**插在**全域設定的路由之前，並強制 `continue: true`；在預設的 `alertmanagerConfigMatcherStrategy: OnNamespace` 下，還會替每條路由（以及 inhibit rule）加上 `namespace="<CR 所在 namespace>"` matcher。後果有三：平台路由排不到最前面；租戶路由只匹配帶 `namespace=<CR namespace>` 的告警；租戶的 custom alert 匹配後照樣往下走進全域路由，隔離不成立。所以平台不再產生 AlertmanagerConfig CR。

⚠️ v2.9.0 映像仍是舊行為：`operator-generate` 的 `all` 含 `alertmanager`，會讀 conf.d、為每個租戶產出一份 AlertmanagerConfig；`generate-routes` 沒有 `--output-alertmanager`。本頁的流程需要比 v2.9.0 新的 da-tools；用 v2.9.0 映像時，`operator-generate` 改跑 `--components rules` 與 `--components servicemonitor` 各一次，不要 apply 它產出的 AlertmanagerConfig。<!-- image-caveat: v2.9.0 -->

## Prerequisites

```bash
kubectl get alertmanager -n monitoring                      # Alertmanager CR 的名稱與 namespace
kubectl get alertmanager -n monitoring \
  -o jsonpath='{.items[0].spec.configSecret}'               # 目前指向的 Secret（空 = alertmanager-<CR 名稱>）
```

## Step 1: 準備來源（你自己的 Alertmanager 設定）

base 是**你自己的** Alertmanager 設定：global、你自己的 receiver、你自己的路由與 inhibit rule。它必須是 Alertmanager 收得下的完整設定（至少有 `route.receiver` 與對應的 receiver）。

- **kube-prometheus-stack 使用者**：就是你原本寫在 values `alertmanager.config` 的那一段，原樣存成檔（例如 `alertmanager.base.yaml`）進 git。
- ⛔ **不要**拿 Operator 寫出的 `alertmanager-<CR 名稱>-generated` Secret 當 base：那是 Operator 的輸出，已經混進 AlertmanagerConfig CR 的路由。
- 先前貼過平台產物（含 `tenant-*`／`platform-enforced*` receiver，或第一行是 `# GENERATED by da-tools generate-routes`）的設定會被拒收、結束碼 1；把貼進去的部分刪掉，留下你自己原本的設定。

**Watchdog**：kube-prometheus-stack 預設設定把 `Watchdog` 送到 `null` receiver。合併後平台的 Watchdog 路由排在最前面、先匹配，所以 base 裡那條不再收到 Watchdog（留著無害）。要把心跳接到外部 dead-man's switch，在 base 裡定義 `watchdog-heartbeat` receiver（例如以 `url_file` 指向掛載的 Secret）；沒接任何 integration 時 `generate-routes` 報 `watchdog_undelivered`（見 [cli-reference §generate-routes](../cli-reference.md#generate-routes)、[告警平面自我存活性](alerting-plane-self-liveness.md)）。

## Step 2: 產出 alertmanager.yaml

```bash
# CI 先判整棵樹
da-tools generate-routes --config-dir conf.d --validate --strict

# 合併：輸出 = 合併(來源 base, conf.d)
da-tools generate-routes --config-dir conf.d --output-alertmanager \
  --base-config alertmanager.base.yaml -o alertmanager.yaml \
  --secret-mounts-out secret-mounts.json
```

conf.d 改了就拿**同一份** `alertmanager.base.yaml` 再跑一次，不要拿上一次的 `alertmanager.yaml` 當 base。`-o` 指向 base 是結束碼 2。

**Receiver 與憑證**：receiver 由各租戶 `_routing` 宣告，型別、`secretRef` 寫法與檢查與 ConfigMap 路徑完全相同，見 [BYO 整合指南 §5](byo-alertmanager-integration.md#憑證放在-secretsecretref)。`secretRef` 渲染成 `<field>_file: /etc/alertmanager/secrets/<secret-name>/<key>`（根目錄可用 `--secret-mount-root` 改）。Operator 會把 Alertmanager CR `spec.secrets` 列出的每個 Secret 掛在 `/etc/alertmanager/secrets/<secret-name>/`，正好是這個版面——所以每個被引用的 Secret（`da-<tenant>`、policy `shared_secrets` 列的共用 Secret）都要列進 `spec.secrets`，並與 Alertmanager CR 在同一個 namespace。

**要掛哪些 Secret 不必自己數**（[#1560](https://github.com/vencil/Dynamic-Alerting-Integrations/issues/1560)）：上面的 `--secret-mounts-out` 把 `alertmanager.yaml` 實際會讀的 Secret 寫成 `secret-mounts.json`——從產出的設定本身走訪每個 `*_file`，所以 base 自己的（例如 `watchdog-heartbeat` 的 `url_file`）也在內；只有名稱與 key，沒有值。`spec.secrets`（Step 4）照它的 `secrets[].name` 列，套用後用 `operator-check --secret-mounts` 對照（見 [Troubleshooting](#troubleshooting)「Secret 不存在」）。`other_files` 是掛載根目錄以外的路徑，Operator 的 `spec.secrets` 掛不到，要另外處理。Operator 路徑不要改 `--secret-mount-root`：Operator 一律掛在 `/etc/alertmanager/secrets/`，改了 `operator-check` 會判 FAIL。

**抑制規則**：severity dedup 與 sentinel 抑制同 ConfigMap 路徑，由 `generate-routes` 產生；Operator 路徑不再有另一套。

## Step 3: 寫入 Secret

```bash
kubectl create secret generic da-alertmanager-config -n monitoring \
  --from-file=alertmanager.yaml --dry-run=client -o yaml | kubectl apply -f -
```

- ⛔ **key 必須是 `alertmanager.yaml`**：Operator 只讀這個 key。`--from-file=alertmanager.yaml` 以檔名當 key，所以輸出檔請就叫這個名字。Secret 裡的其他 key 會被複製進 Operator 產生的 Secret，掛在 `/etc/alertmanager/config/` 當額外檔案（例如模板）。
- ⚠️ Secret 不存在或沒有 `alertmanager.yaml` 這個 key 時，Operator 不會報錯停下，而是佈一份只有一個空 receiver 的最小設定——**所有通知都會被丟掉**。改名或改 key 後務必照 [Troubleshooting](#troubleshooting) 確認。
- Secret 名稱不要用 `alertmanager-<CR 名稱>-generated`（Operator 自己的輸出）。
- base 裡若有明文憑證，這個 Secret 也會有；GitOps 時用 Sealed Secrets 或 External Secrets Operator 管理，見 [Operator GitOps 部署](operator-gitops-deployment.md)。

## Step 4: 讓 Alertmanager CR 指向它

**直接管理 Alertmanager CR**：

```yaml
apiVersion: monitoring.coreos.com/v1
kind: Alertmanager
metadata:
  name: main
  namespace: monitoring
spec:
  configSecret: da-alertmanager-config
  secrets:                      # secret-mounts.json 的每個 secrets[].name
    - da-db-a
```

不要同時設 `spec.alertmanagerConfiguration`：它設了就優先於 `configSecret`。

**kube-prometheus-stack**：

```yaml
alertmanager:
  alertmanagerSpec:
    useExistingSecret: true     # 不再由 chart 以 alertmanager.config 渲染自己的 Secret
    configSecret: da-alertmanager-config
    secrets:
      - da-db-a
```

`useExistingSecret: true` 時 chart 忽略 `alertmanager.config`（含 `templateFiles`），那一段已經搬進 Step 1 的 base。

### AlertmanagerConfig CR 仍會排在前面

Alertmanager CR 也選取 AlertmanagerConfig CR 時（`alertmanagerConfigSelector`／`alertmanagerConfigNamespaceSelector` 有設；**kube-prometheus-stack 預設就把 selector 設成 `{}`，選取所在 namespace 的全部 AlertmanagerConfig**），Operator 仍把那些 CR 的路由插在 `configSecret` 的路由之前，帶強制的 `continue: true` 與 namespace matcher。

- 平台自己的 CR 不再產生；升級前留下的請刪掉（`operator-check` 第 4 項會對它們 warn）：

  ```bash
  kubectl delete alertmanagerconfig -n monitoring -l app.kubernetes.io/part-of=dynamic-alerting
  ```

- 其他團隊的 CR 照樣排在最前面。因為強制 `continue: true`，它們擋不住告警往下走到平台路由，但匹配到的告警**也會**由它們的 receiver 送出一份。
- 不要任何東西排在平台路由前面：把 selector 設成不匹配任何 AlertmanagerConfig，例如：

  ```yaml
  alertmanager:
    alertmanagerSpec:
      alertmanagerConfigSelector:
        matchLabels:
          dynamic-alerting.io/no-alertmanagerconfig: "true"   # 沒有任何 CR 帶這個 label
  ```

這條路徑上沒有平台的 CR，所以先前「租戶路由只匹配帶 `namespace=<CR namespace>` 的告警」的問題不存在。

## 從 per-tenant AlertmanagerConfig 遷移

先前以 `operator-generate --components alertmanager`（或 `all`）或 `migrate-to-operator` 部署了 per-tenant AlertmanagerConfig 的叢集：

1. 照 Step 1–4 產出 Secret、讓 Alertmanager CR 指向它。
2. 刪掉平台留下的 CR（上面的 `kubectl delete alertmanagerconfig …`）。1 與 2 之間，舊 CR 匹配得到的租戶告警可能由新舊兩邊各送一份；順序反過來則會有一段沒有租戶路由。
3. `da-tools operator-check --namespace monitoring`：第 4 項 pass 代表沒有殘留。

`operator-generate --components alertmanager` 與 AlertmanagerConfig 專用旗標（`--config-dir`、`--api-version`、`--receiver-template`、`--secret-name`、`--secret-key`）現在是結束碼 2，見 [cli-reference §operator-generate](../cli-reference.md#operator-generate)。

## Troubleshooting

### 通知全部不見

```bash
kubectl get alertmanager -n monitoring -o jsonpath='{.items[0].spec.configSecret}'
kubectl get secret da-alertmanager-config -n monitoring -o jsonpath='{.data}' | jq 'keys'
```

Secret 名稱對不上、或 key 不是 `alertmanager.yaml`，Operator 會改用只有一個空 receiver 的最小設定（見 Step 3）。

### 確認實際生效的路由順序

```bash
kubectl port-forward -n monitoring svc/alertmanager-operated 9093 &
curl -s localhost:9093/api/v2/status | jq -r '.config.original'
```

`route.routes` 的開頭應是平台 4 條路由。排在它們前面、receiver 名稱形如 `<namespace>/<CR 名稱>/<receiver>` 的路由來自 AlertmanagerConfig CR，處理方式見上方「AlertmanagerConfig CR 仍會排在前面」。

### `generate-routes` 拒收 base（結束碼 1）

base 是先前的輸出（第一行是 `# GENERATED by da-tools generate-routes`）或含 `tenant-*`／`platform-enforced*` receiver。改用你自己的設定，見 Step 1。

### Secret 不存在（`*_file` 讀不到）

```bash
da-tools operator-check --namespace monitoring --secret-mounts secret-mounts.json
kubectl get secret -n monitoring | grep da-
```

被 `secretRef` 引用的 Secret 要與 Alertmanager CR 同一個 namespace，並列在 `spec.secrets`。`operator-check` 的「Secret 掛載」一列拿 Step 2 寫出的清單比對每個 Alertmanager CR 的 `spec.secrets`（`--alertmanager <名稱>` 只比一個）：清單有、`spec.secrets` 沒有 ⇒ FAIL，讀那個 Secret 的 receiver 送出時就失敗、那則通知遺失；`spec.secrets` 多列了 `da-` 開頭、設定沒讀的 ⇒ WARN，那個 Secret 不存在時 Pod 起不來。它只讀 CR，不讀 Secret，所以 Secret 存不存在、裡面有沒有那個 key，仍要用上面的 `kubectl get secret` 看。已經漏掉時，平台 rule pack 的 `AlertmanagerNotificationsFailing`（webhook 以外的 integration）與 `AlertmanagerWebhookNotificationsFailing`（webhook）會在送出失敗後報出。
