# Operator Alertmanager Integration Guide

> **Language / 語言：** **English (Current)** | [中文](./operator-alertmanager-integration.md)

## Overview

In a Prometheus Operator environment, alert routing is rendered by **the same generator** as on the ConfigMap path: [`da-tools generate-routes`](../cli-reference.en.md#generate-routes) merges the conf.d tenant routes into your own Alertmanager config and writes one complete `alertmanager.yaml`; you put it in a Secret and point the Alertmanager CR's `spec.configSecret` at it. On the Operator path, `operator-generate` produces only PrometheusRule and ServiceMonitor (see [Operator Prometheus Integration](operator-prometheus-integration.en.md)).

The order of `route.routes` in the output is the same as on the ConfigMap path: the 4 platform routes (Watchdog heartbeat, the `component="custom"` isolation subtree with its per-tenant children, synthetic probe, sentinel) come first, then your base's own routes in their original order, then the tenant routes. The base is a source, never an earlier output (an output's first line is the `# GENERATED by da-tools generate-routes` marker, and a base carrying it is refused). Merge rules and exit codes: [cli-reference §generate-routes](../cli-reference.en.md#generate-routes).

**Why not the AlertmanagerConfig CRD** ([#3572](https://github.com/vencil/Dynamic-Alerting-Integrations/issues/3572)): the Prometheus Operator **prepends** an AlertmanagerConfig CR's routes before the global config's routes and forces `continue: true` on them; with the default `alertmanagerConfigMatcherStrategy: OnNamespace` it also adds a `namespace="<CR namespace>"` matcher to every route (and inhibit rule). Three consequences: the platform routes cannot come first; tenant routes only match alerts that carry `namespace=<CR namespace>`; and a tenant's custom alert, once matched, continues into the global routes, so isolation does not hold. The platform therefore no longer generates AlertmanagerConfig CRs.

⚠️ The v2.9.0 image still has the old behaviour: `operator-generate`'s `all` includes `alertmanager`, reads conf.d and emits one AlertmanagerConfig per tenant; `generate-routes` has no `--output-alertmanager`. The procedure on this page needs a da-tools newer than v2.9.0; with the v2.9.0 image, run `operator-generate` once with `--components rules` and once with `--components servicemonitor`, and do not apply any AlertmanagerConfig it emits. <!-- image-caveat: v2.9.0 -->

## Prerequisites

```bash
kubectl get alertmanager -n monitoring                      # name and namespace of the Alertmanager CR
kubectl get alertmanager -n monitoring \
  -o jsonpath='{.items[0].spec.configSecret}'               # the Secret it points at now (empty = alertmanager-<CR name>)
```

## Step 1: Prepare the source (your own Alertmanager config)

The base is **your own** Alertmanager config: global, your own receivers, your own routes and inhibit rules. It must be a complete config Alertmanager accepts (at least `route.receiver` and that receiver).

- **kube-prometheus-stack users**: it is the block you used to put under `alertmanager.config` in your values; save it as is to a file (e.g. `alertmanager.base.yaml`) in git.
- ⛔ Do **not** use the Operator's `alertmanager-<CR name>-generated` Secret as the base: that is the Operator's output and already has the AlertmanagerConfig CRs' routes mixed in.
- A config into which platform output was pasted before (it has `tenant-*` / `platform-enforced*` receivers, or its first line is `# GENERATED by da-tools generate-routes`) is refused with exit 1; delete the pasted parts and keep your own original config.

**Watchdog**: kube-prometheus-stack's default config sends `Watchdog` to the `null` receiver. After the merge the platform's Watchdog route comes first and matches first, so that route in the base no longer receives Watchdog (keeping it is harmless). To wire the heartbeat to an external dead-man's switch, define the `watchdog-heartbeat` receiver in the base (e.g. with `url_file` pointing at a mounted Secret); with no integration on it, `generate-routes` reports `watchdog_undelivered` (see [cli-reference §generate-routes](../cli-reference.en.md#generate-routes) and [alerting-plane self-liveness](alerting-plane-self-liveness.en.md)).

## Step 2: Produce alertmanager.yaml

```bash
# CI judges the whole tree first
da-tools generate-routes --config-dir conf.d --validate --strict

# Merge: output = merge(source base, conf.d)
da-tools generate-routes --config-dir conf.d --output-alertmanager \
  --base-config alertmanager.base.yaml -o alertmanager.yaml
```

When conf.d changes, run it again with the **same** `alertmanager.base.yaml`; never use the previous `alertmanager.yaml` as the base. `-o` pointing at the base is exit 2.

**Receivers and credentials**: receivers are declared in each tenant's `_routing`; the types, the `secretRef` shape and its checks are exactly those of the ConfigMap path, see [BYO integration guide §5](byo-alertmanager-integration.en.md#credentials-in-a-secret-secretref). A `secretRef` is rendered as `<field>_file: /etc/alertmanager/secrets/<secret-name>/<key>` (change the root with `--secret-mount-root`). The Operator mounts every Secret listed in the Alertmanager CR's `spec.secrets` at `/etc/alertmanager/secrets/<secret-name>/`, which is exactly that layout — so every referenced Secret (`da-<tenant>`, the shared Secrets listed in the policy's `shared_secrets`) must be listed in `spec.secrets` and live in the Alertmanager CR's namespace.

**Inhibit rules**: severity dedup and sentinel inhibition are produced by `generate-routes`, as on the ConfigMap path; the Operator path no longer has a second set.

## Step 3: Write the Secret

```bash
kubectl create secret generic da-alertmanager-config -n monitoring \
  --from-file=alertmanager.yaml --dry-run=client -o yaml | kubectl apply -f -
```

- ⛔ **The key must be `alertmanager.yaml`**: the Operator reads only that key. `--from-file=alertmanager.yaml` uses the file name as the key, so name the output file exactly that. Other keys in the Secret are copied into the Secret the Operator generates and mounted under `/etc/alertmanager/config/` as extra files (templates, for example).
- ⚠️ When the Secret is missing or has no `alertmanager.yaml` key, the Operator does not stop with an error: it provisions a minimal config with one empty receiver — **every notification is dropped**. After renaming the Secret or its key, check with [Troubleshooting](#troubleshooting).
- Do not name the Secret `alertmanager-<CR name>-generated` (the Operator's own output).
- If the base holds credentials in clear text, so does this Secret; under GitOps manage it with Sealed Secrets or the External Secrets Operator, see [Operator GitOps Deployment](operator-gitops-deployment.en.md).

## Step 4: Point the Alertmanager CR at it

**Managing the Alertmanager CR directly**:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: Alertmanager
metadata:
  name: main
  namespace: monitoring
spec:
  configSecret: da-alertmanager-config
  secrets:                      # every Secret a secretRef references
    - da-db-a
```

Do not also set `spec.alertmanagerConfiguration`: when set, it takes precedence over `configSecret`.

**kube-prometheus-stack**:

```yaml
alertmanager:
  alertmanagerSpec:
    useExistingSecret: true     # the chart stops rendering its own Secret from alertmanager.config
    configSecret: da-alertmanager-config
    secrets:
      - da-db-a
```

With `useExistingSecret: true` the chart ignores `alertmanager.config` (including `templateFiles`); that block moved into the base in Step 1.

### AlertmanagerConfig CRs still go first

When the Alertmanager CR also selects AlertmanagerConfig CRs (`alertmanagerConfigSelector` / `alertmanagerConfigNamespaceSelector` set; **kube-prometheus-stack sets the selector to `{}` by default, which selects every AlertmanagerConfig in its namespace**), the Operator still prepends those CRs' routes ahead of the `configSecret`'s routes, with the forced `continue: true` and the namespace matcher.

- The platform's own CRs are no longer generated; delete the ones left from before the upgrade (`operator-check` check 4 warns about them):

  ```bash
  kubectl delete alertmanagerconfig -n monitoring -l app.kubernetes.io/part-of=dynamic-alerting
  ```

- Other teams' CRs still go first. Because of the forced `continue: true` they cannot stop an alert from reaching the platform routes, but an alert they match is **also** delivered by their receivers.
- To have nothing ahead of the platform routes, set the selector so it matches no AlertmanagerConfig, for example:

  ```yaml
  alertmanager:
    alertmanagerSpec:
      alertmanagerConfigSelector:
        matchLabels:
          dynamic-alerting.io/no-alertmanagerconfig: "true"   # no CR carries this label
  ```

There are no platform CRs on this path, so the former problem of tenant routes only matching alerts that carry `namespace=<CR namespace>` does not arise.

## Migrating from per-tenant AlertmanagerConfigs

On a cluster where per-tenant AlertmanagerConfigs were deployed with `operator-generate --components alertmanager` (or `all`) or `migrate-to-operator`:

1. Follow Steps 1–4 to produce the Secret and point the Alertmanager CR at it.
2. Delete the platform's leftover CRs (the `kubectl delete alertmanagerconfig …` above). Between 1 and 2, a tenant alert the old CRs match may be delivered twice, once by each side; in the reverse order there is a window with no tenant routes.
3. `da-tools operator-check --namespace monitoring`: check 4 passing means nothing is left over.

`operator-generate --components alertmanager` and the AlertmanagerConfig-only flags (`--config-dir`, `--api-version`, `--receiver-template`, `--secret-name`, `--secret-key`) now exit 2, see [cli-reference §operator-generate](../cli-reference.en.md#operator-generate).

## Troubleshooting

### No notifications at all

```bash
kubectl get alertmanager -n monitoring -o jsonpath='{.items[0].spec.configSecret}'
kubectl get secret da-alertmanager-config -n monitoring -o jsonpath='{.data}' | jq 'keys'
```

If the Secret name does not match, or the key is not `alertmanager.yaml`, the Operator falls back to a minimal config with one empty receiver (see Step 3).

### Check the route order actually in effect

```bash
kubectl port-forward -n monitoring svc/alertmanager-operated 9093 &
curl -s localhost:9093/api/v2/status | jq -r '.config.original'
```

`route.routes` should start with the 4 platform routes. Routes ahead of them whose receiver names look like `<namespace>/<CR name>/<receiver>` come from AlertmanagerConfig CRs; see "AlertmanagerConfig CRs still go first" above.

### `generate-routes` refuses the base (exit 1)

The base is an earlier output (first line `# GENERATED by da-tools generate-routes`) or has `tenant-*` / `platform-enforced*` receivers. Use your own config, see Step 1.

### Secret not found (`*_file` cannot be read)

```bash
kubectl get secret -n monitoring | grep da-
kubectl get alertmanager -n monitoring -o jsonpath='{.items[0].spec.secrets}'
```

A Secret referenced by a `secretRef` must be in the Alertmanager CR's namespace and listed in `spec.secrets`.
