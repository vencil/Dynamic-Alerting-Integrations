# vibe-adr-writing — ADR 寫給誰、寫什麼、拿掉什麼

## 讀者與他要帶走的五件事

讀者是沒參與討論、要在這個決策之上工作的人：新進工程師、接手的 SRE、半年後的作者自己。讀完他要能回答下面五件事，每件在文中都有對應的段落：

1. **決策**：決定了什麼。一兩句，放在第一屏。
2. **脈絡**：為什麼需要決定；不決定會怎樣。
3. **選項與取捨**：考慮過哪些做法，各自為什麼沒選。
4. **後果與限制**：選了之後要承擔什麼、已知的例外、不涵蓋的範圍。
5. **範例**：一段能實際對照的設定片段，或「輸入 → 輸出」。讀者照著跑，要得到同樣的結果。

章節順序建議：狀態 → 背景 → 決策（含範例）→ 後果與已知限制 → 考慮過的替代方案 → 相關。修訂直接併進它改的那一段，在「狀態」記一行日期與一句摘要；不要在文末一段段往下疊。

## 要拿掉或改寫的

| 類型 | 長相 | 處理 |
|---|---|---|
| 內部代號 | 波次、第 0 步、0-B、D10、E3、選項 P2、Phase 3、「某某 Foundation 第二塊」 | 刪掉，寫出它指的那件事 |
| 歷史敘事 | 「原本寫的是……後來證偽」、「#1234 之前……」、「本文已被推翻三次」 | 刪。歷史歸 CHANGELOG 與 issue；ADR 只寫現在的決策與現在的行為，文末「相關」最多列連結 |
| 票號堆疊 | 一句話後面掛好幾個 issue／PR 號 | 正文只留讀者真的需要點的那個（例如未解限制所屬的 issue） |
| 專案內縮寫 | L0、hier、noop、GRAR | 換成白話，或第一次出現時解釋 |
| 未解釋的外部名詞 | debounce、canonical JSON、inotify、deep merge | 第一次出現給一句白話解釋，或直接換白話 |
| 實作細節當主角 | 函式名、變數名串成的句子 | 決策段寫行為；需要指路時集中到一處「實作位置」 |
| 警示符號氾濫 | 每句都有 ⛔ ⚠️ | 只留在真的會讓讀者踩坑的那一句 |

## 要守住的技術品質

- **每個事實句都對照現行行為。** 寫或改的當下在 head 上實測（跑工具、看輸出），量測記在工作筆記，不進 ADR。量不到就刪，不要改寫成較窄、聽起來較安全的版本：那只是用一句新的未驗證句子換掉舊的（[`agent-rulebook.md`](../../../docs/internal/agent-rulebook.md) D-09：描述現況的肯定句要先驗證）。
- **只改表達時不改決策。** 讀者照新版做出的結果要與舊版相同；已經過審的段落只調措辭，不動語意。
- **範例的輸出是真的跑出來的。** 改了範例的輸入就重跑。
- **中英兩份語意一致。** `foo.md`（中文，主版本）與 `foo.en.md` 同一輪改，段落一一對應。
- **狀態與日期正確。** frontmatter 的 `status`／`updated_at`、`## 狀態` 段落三者一致。改了標題要跑 `make adr-index`，並找出其他文件對舊標題或段落名稱的引用一起改。

## 自檢清單

- [ ] 第一屏看得到決策本身。
- [ ] 五件事各有段落；範例同時有輸入與輸出。
- [ ] 沒有代號與歷史敘事，下面三條 grep 的每個命中都有理由：
  - 代號與敘事：`grep -nE '波次|第 ?[0-9] ?步|Phase [0-9]|[0-9]-[A-Z][^A-Za-z]|[0-9]-[A-Z]$|\b[A-Z][0-9]{1,2}\b|證偽|原本寫|Amendment' <檔>`
  - 表格列裡的專案縮寫：`grep -nE '^\|.*\b[A-Z]{2,}[0-9]*\b' <檔>`（把命中的縮寫逐一確認在文中有解釋）
  - 票號堆疊（一行兩個以上）：`grep -nE '#[0-9]+.*#[0-9]+' <檔>`
  - ⚠️ 代號緊貼中文時（例如「見0-B」）`\b` 不成立、grep 會漏，這幾種要人工掃一遍。
- [ ] 每個專案內縮寫與外部名詞第一次出現時有白話解釋。
- [ ] 每個描述行為的句子都有這一輪的量測。
- [ ] 中英段落對應；狀態與日期一致。
- [ ] `make lint-docs` 與 `python3 scripts/tools/lint/check_doc_links.py --ci` 通過。

## 分工

一句事實能不能寫、要配什麼證據，走 `verifying-claims`；改完請沒參與的人盲審，走 `vibe-subagent-review`；還在決定要做什麼，走 `vibe-brainstorm`。
