IDENTITY (ADR-027 §2, §3; GHSA-3g2h-rf85-5rrv) — the API is served only on a
  pod-internal Unix socket ({{ include "tenant-api.humanSocketPath" . }}) behind the oauth2-proxy
  sidecar, which reads the same config file tenant-api does. Port 8080 serves
  only /health, /ready and /metrics; a request there carrying an identity header
  (X-Forwarded-Email, X-Forwarded-Groups or a configured claim header) is
  answered 400. A client that still calls the API on 8080 gets 404: point it at
  the oauth2-proxy port (Service port `http`).

NetworkPolicy only works if your CNI ENFORCES it. Flannel (base) and some managed
  "simple" CNIs SILENTLY IGNORE NetworkPolicy: the API server accepts it and this
  install succeeds, but port 8080 is left open to the whole cluster (security
  theater). Use a NetworkPolicy-aware CNI (Calico / Cilium / Antrea) and verify by
  sending a packet that SHOULD be denied — do not trust a successful install. The
  CNI-independent root-cause fix is L7 identity verification (roadmap #5); this
  policy is L4 defense-in-depth.

GENERATOR CONTAINER (ADR-036 §3, required since #2903) — image {{ .Values.generator.image.repository }}:{{ .Values.generator.image.tag }}{{ with .Values.generator.image.digest }}@{{ . }}{{ end }}.
  tenant-api asks `da-tools generator-service` (pod-internal Unix socket,
  /conf.d read-only) before every write that changes a conf.d file; only a
  pass is committed. While it does not answer, every such write is refused
  (503 VALIDATOR_UNAVAILABLE); reads keep working.
  That image MUST ship generator-service. tools/v2.9.0 — the chart's default
  pin until the next da-tools release raises it — does NOT: set
  generator.image to an image that does. With generator.image.digest set the
  digest is what runs: changing only the tag changes nothing, so update (or
  clear) the digest too; both must name an image with generator-service.

RECIPE-PREVIEW CONTAINER (ADR-027 §5, #1040) — image {{ .Values.recipePreview.image.repository }}:{{ include "tenant-api.recipePreviewTag" . }}{{ with .Values.recipePreview.image.digest }}@{{ . }}{{ end }}.
  Answers POST /api/v1/tenants/{id}/recipe-preview for tenant-api over a
  pod-internal Unix socket; while the running service does not answer, that
  route returns 503 PREVIEW_UNAVAILABLE and nothing else is affected. While
  the container restarts (an OOM kill, a liveness restart), the whole pod is
  not Ready: Kubernetes counts every container. The image is built by the
  tools/v* release, and its tag follows generator.image.tag. tools/v2.9.0
  built NO recipe-preview image: until the next da-tools release, an image
  that cannot be pulled keeps this pod from becoming Ready (Kubernetes counts
  every container), so set recipePreview.enabled=false or point
  recipePreview.image at an image you built.
